01 / Market Taxonomy

The 5 Agent Sandboxing Archetypes

Execution environments are not interchangeable VMs. Group them by who controls the runtime and files:

Tier 1

Model-Native

Gemini

Code runs inside the LLM prompt turn. Zero app orchestration, fixed libraries, no OS lifecycle control.

Tier 2

Databricks SQL

Unity Catalog MCP python_exec — measured

Stateless Python over serverless SQL warehouses via MCP JSON-RPC, inside strict lakehouse data boundaries. Sandbox Beta surfaces exist but were not measurable here.

Tier 3

Agent Workspace APIs

E2B / Modal / Blaxel / Daytona

Dedicated microVMs & containers with native binary file I/O, custom images, shell, and state persistence.

Tier 4

Cloud Interpreters

Google Vertex / AWS AgentCore

Managed cloud tools integrated with enterprise IAM, VPC networking, S3/EFS mounts, and CMEK.

Tier 5

Self-Operated Fleet

Kubernetes / OpenSandbox / VMs

Apache-2.0 or K8s CRD controllers on your own nodes. Full policy ownership; you pay for idle warm pools & ops.

Product Selection Rule: Compare the exact execution surface—not the cloud brand logo. Databricks SQL python_exec, Dedicated Sandbox Beta, and Unity Catalog MCP are three completely different products.
02 / Practical Scenarios

Matching Real Product Workflows to Sandbox Tiers

How Product Managers and Architects should map user features to infrastructure:

Scenario A: Autonomous Coding & QA Agent

"Clone repo, fix CSV parser bug, run pytest"

Needs: Multi-call file persistence, offline/custom packages, exception recovery, byte-exact diff output.

Shortlist: E2B, Modal (Tier 3)

Both passed 5/5 on repository test-fixing, cross-call filesystem state, and error recovery.

Scenario B: Enterprise Financial Data Analyst

"Upload 26.9 KB binary + 10k-row CSV, return summary"

Needs: Strict air-gapped network (no data exfiltration), binary file integrity, cloud IAM governance.

Shortlist: Google Default Code Sandbox, E2B, Modal

Google's default code sandbox blocks outbound internet by default and passed 5/5 binary & CSV pipeline checks.

Scenario C: Interactive Web App Builder

"Spin up dev server, expose live preview URL, pause overnight"

Needs: Port forwarding / preview tokens, standby snapshots, persistent volumes across restarts.

Shortlist: Blaxel, E2B, Daytona, Modal

Blaxel and Daytona document rich preview/standby features, though Blaxel's stdout adapter path needs repair first.

Scenario D: GPU Workload / Heavy Compute

"Run CUDA embeddings or local model evaluation"

Needs: Explicit GPU reservation (T4/L4/A100/H100), custom container images, preemption handling.

Shortlist: Modal, Daytona, GKE / Compute Engine VMs

E2B is strictly CPU-only. Modal requires gvisor for GPUs; Daytona deletes GPU sandboxes on stop.

05 / Reliability Deep Dive

Why "HTTP 200 OK" Still Breaks Your Agent

We printed exactly 131,072 UTF-8 bytes of ordered Unicode text (`café`, `λ`). Every API reported `status: success`:

Measured Stdout Payload Integrity (5 Trials Each)

E2B, Modal, Google Code (5/5 Passed) 131,072 / 131,072 Bytes (Exact)
AWS AgentCore Interpreter (0/5 Passed) 131,071 Bytes (Missing Final \n)
Blaxel (0/5 Passed) 65,602 Bytes (~50% Truncated)

Note: Reflects the tested SDK stdout paths, not provider-wide native file limits.

Real-World Impact on Product Features

  • 1 Missing Byte Breaks Git Patches (AWS):
    If a coding agent prints a unified diff or hash-verified payload over stdout and the transport strips the final newline (`131,071` vs `131,072` bytes), strict consumers and parsers fail.
  • 65 KB Log Truncation Breaks JSON Tooling (Blaxel):
    Blaxel's process log inserted a truncation banner halfway through the stream (`65,602` bytes). Any agent returning large JSON/CSV data over stdout will crash.
  • Architectural Fix:
    Never use stdout or UTF-8 string decoding (`errors="ignore"`) to transport large artifacts. Always use native binary file APIs (`read_bytes` / `write_bytes`).
Benchmarking Lesson: Checking `exit_code == 0` is not an evaluation. Always validate the exact returned bytes and SHA-256 hashes at the host.

09 / Actionable Playbook

How to Choose & Reproduce This Benchmark

Run your workload through 5 gating questions, measure gross campaign cost, and inspect the raw evidence:

The 5 Architecture Gating Questions

Filter Your Shortlist Before Benchmarking

  1. State Contract: Do you need live files across calls, durable disk after stop, or full memory resume?
  2. Hardware & GPUs: Do you need CPU-only (E2B/Google) or preemptible/dedicated GPUs (Modal/Daytona)?
  3. Data Boundary: Have you audited all 6 surfaces (compute, logs, snapshots, volumes, control plane, LLM)?
  4. Failure & Cancellation: Does the adapter preserve exact bytes and kill timed-out remote processes?
  5. Gross Cost per Verified Completion:
    (Active/Idle Compute + Storage + Egress + Tokens + Retries) ÷ Verified Completions
